# Inox: Two Versions — Scripting (Obvious for Agents) vs System Programming (l9 + COP)

User's explicit framing (2026):

> my idea is that the "scripting" version should be fairly "obvious" for coding Agents ; whereas the "system programming" cannot be obvious because it manipulate more complex and much less usual concepts ; hence the two versions

## The split and why it exists

There are two intended "versions" / layers / audiences for Inox:

1. **Scripting layer** (the default, minimal CLI path)
   - Files: `bootstrap.nox` + `forth.nox` + `cli-stdlib.nox`
   - Activated by default (`node builds/inox.js prog.nox` or `bin/inox.js` etc.). No env var needed.
   - Goal: a **usable, rich enough, old-school** concatenative scripting language (Forth/C/Unix flavour) with modern script ergonomics for data modeling and updates.
   - **"Fairly obvious for coding Agents"**: this is the key point. Agents (whether prompt-driven LLM agents, human coders, or other generators) should be able to write or emit natural `.nox` code for their inner loop without deep surprise.
     - Working memory as maps/records (`map.new`, `remember`/`recall`/`update!`, `/key` tag keys).
     - Easy branching for exploration of the possible (`fork-memory`, `with-update` derivation).
     - Simple control of side-effects (the `begin-turn` / `delay-effect` / `commit-turn` / `obsolete-turn` / `obsolete` pattern sketched in cli-stdlib).
     - Capitalization of reusable sub-results (just remember a sub-map under a cache key).
     - Poor-man's namespacing (`text.length`, `array.get`, `map.put`, `file.read`, `float.sqrt`, `stack.push`... + poly dispatchers where stable).
     - Classic explicit postfix, named values (`>x $x`), `!` for effects, `it` + `with` for context.
   - Relation to mainstream: higher expressiveness in composition, metaprogramming, explicit dataflow, low-ceremony CLI tools; lower (for now) in nested data ergonomics compared to Python dict+dataclass / Ruby hash+Struct / JS object / Lua table — addressed here via records + maps + with-style + the update words.
   - This layer is what we produce while Inox matures, and what transitional JS/COP bridges can consume.
   - Budget visibility at this level should remain simple: estimated cost, remaining budget, degraded mode, ask/abort. The full CXU accounting machinery belongs below, in the system layer.

2. **System programming layer** (l9 + COP + future dynamic objects/actors)
   - Opt-in: `INOX_WITH_L9=1` (or `INOX_FULL=1`).
   - **FBF status (2026-11-22, GPT-6 coding agent under Jean Hugues Noel Robert):** the opt-in startup now loads `l9.nox` **and** `stdlib.nox` without the previous assertion; the focused `npm run test:l9` suite exercises class extension, basic integer method dispatch, recursion and `integer.times`. This is **bootstrap + verified subset**, not completion of the actor/task/promise layer.
   - **FBF loop-core repair (2026-11-22, GPT-6 under Jean Hugues Noel Robert):** `loop-while` and `loop-until` now repeat according to their respective booleans, preserve their permanent control frames, and resume at the correct instruction after the loop sentinel. The formerly unconditional `debug()` in `loop-until` was removed. `from:to:do:`, `from:down-to:do:` and `from:to:by:do:` use explicit postfix comparisons and the repaired **iterative** loop core, not recursive fallback. `npm run test:loop-control` validates 82 cases across both modes (including zero-step rejection with a pending FATAL diagnostic issue): results, break-if, after-loop continuation, nested iteration and constant control depth through 1,000 iterations in both modes.
   - **L9 integer.times repair (2026-11-22, GPT-6 under Jean Hugues Noel Robert):** removed the former recursive `stdlib.times-loop` workaround. The direct `times/it-method{ >blk from: 1 to: it do: { $blk .run }; }` is valid once the nested infix `do:` is terminated by `;` and the block is retrieved explicitly as a local value (`$blk`), rather than invoking an unrelated word `block`. The first failure was a syntax error in generated `stdlib.nox`, **not evidence of a compiler defect**. The L9 suite now verifies 22 cases including nested `.times` and 1,000 repetitions; the caller continuation and control-stack depth are preserved.
   - **L9 task-structure FBF (2026-11-23, GPT-6 under Jean Hugues Noel Robert):** the early `make.task` stub was removed. The actual class `maker{` consumes its class tag plus three stack arguments, and root initialization dynamically resolves the newly registered constructor *after* `task/class{` registration. `l9-root` is now a real task (`reference`, label `root`, id `1`, paused initially); children have parent references, unique IDs and correct `a-fork?` / `a-spawn?` flags, and are registered in the parent's `subtasks` / `forks` arrays. Corrected the unrelated but blocking core defects in extensible-object `object.!` (invalid exact forwarding-area-length assertion), `array.get` (discarded returned element), `stack.push` (overwrote length header and bypassed growth) and `stack.fetch` (off-by-one). Added native `array.each{` using actual array length/index access. `npm run test:l9-tasks` validates 29 runnable cases including collection growth to 100 items, not merely green startup.
   - **L9 elementary lifecycle FBF (2026-11-23, GPT-6 under Jean Hugues Noel Robert):** `@subtasks .each{...}` correctly separates the attribute receiver from dispatch; this repairs **root** cancellation without disabling child propagation. Added missing `list.each{`, using canonical stack length/fetch because list does not inherit stack iteration. Elementary promise `resolve`/`reject` now invoke `it .schedule` as a method, rather than treating `@schedule` as an object field; the handler list uses `@handlers .each{...}` and `@handlers .clear`. `npm run test:l9-lifecycle-basics` checks **15 cases** including list iteration, root cancellation idempotence, pending/settled states, stored values/reasons and first-settlement-wins. These checks do not imply callbacks or actor scheduling work.
   - **L9 promise-chain FBF (2026-11-23, GPT-6 under Jean Hugues Noel Robert):** fixed `make.promise`'s early-bound factory inside `promise-handler`, established concrete handler registration and a returned next-promise through `promise.then(on-resolve, on-reject)` (use `_` for absent callbacks), and passed the settled source explicitly to each registered handler. Crucially, `promise.schedule` now tests *pending* as a true postfix boolean predicate (`@resolved? @rejected? or not`); the former mixed syntax erroneously skipped fulfillment callbacks. The existing local settlement path now propagates values and rejections, transforms callbacks, dispatches late handlers and chained callbacks, and drains handlers once. `npm run test:l9-promise-chain` verifies **17 cases** including two-level chains, independent handlers, first-settlement-wins and caller control-stack restoration. The local implementation is synchronous; actor scheduling and exception-to-rejection remain separate, unfinished contracts.
   - **L9 actor-context FBF (2026-11-24, GPT-6 under Jean Hugues Noel Robert):** root-cause tests demonstrated that the actor payload slot at offset `+6` reserved for saved `CSP` was overwritten with the current L9 task, while the actual `l9-task` slot at `+7` remained void. Corrected both L9 lookup and assignment and added an actor layout assertion; `npm run test:l9-actor-layout` passes **6/6** after **2/6** before. `switch-actor` formerly restored the destination without saving the source. It now consumes the destination operand, saves source IP/TOS/CSP and restores the destination, with **1 isolated function test** using mocked memory (`npm run test:l9-actor-switch`); a real two-actor execution remains to be verified. `task.fork` and `task.spawn` were calling an early-bound `make.task` before its maker registration; they now resolve it dynamically and bind the child task in the new actor's named `l9-task` slot using `stack.put`. Task structure regressions increase to **36/36**. This work changes no per-call/defer checks and does not implement overflow detection.
   - **L9 object-core FBF (2026-11-24, GPT-6 under Jean Hugues Noel Robert):** confirmed an actual failure of superclass dispatch: 10/18 initial object tests passed, while inherited methods/attributes failed. `class{` treated pre-existing implementation verbs (`thing`, `map`) as registered classes and never created their metaclasses; `extend-class{` now registers those class records without overwriting their verb implementations. `superclass` now records the declared parent in metaclass metadata; `make.metaclass` preserves the parent when `update-class` rebuilds the metadata. In the VM, `object.?@` copied into the popped object cell instead of the surviving key/result cell; it now copies before releasing the object reference. The former `run_class_method_on_target` deferred `run-super-method` until after the caller's next instruction, exposing method-definition addresses instead of running the inherited method. The class fallback now resolves and invokes methods synchronously, with a canonical `resolve-method-name` shared by method reflection (`understand?`) and inherited lookup, caching inherited definitions by receiver class. `thing.understand?` also corrects the argument order at its method adapter. `npm run test:l9-object-core` passes **35/35** real-VM cases: class registration, inheritance one/two ancestors deep, inherited accessors, overrides, late parent updates and cache invalidation, independent instances, primitive-type and class-method reflection, 200 inherited calls, caller stack depth, plus observable absent-method behavior. This validates the **tested OO kernel**, not all of L9. **Known separate defect:** the legacy `missing-method` hook emits a useful diagnostic but may then trigger an `Invalid boolean value` assertion during error unwinding. `alias-method` remains unimplemented. No actor scheduler, task exception path or overflow monitoring was added.
   - **L9 scheduler and exception provenance (at the start of 2026-11-24, before the present FBF):** the historical [`l8/lib/l8.js`](https://github.com/virteal/l8/blob/master/lib/l8.js) defines `Task.raise` as injecting a step error, canceling/failing dependent steps and propagating through step scheduling, and `Task.resume` as unblocking a paused step and scheduling its successor. Current L9 lacks corresponding step/error dispatch, ready queue and completed `task.schedule` method; `task.raise` is only an empty scaffold, while `task.pause` and `task.resume` mistakenly access `@schedule` as a field. The current `actor` primitive returns an **integer handle**, unlike reference-returning `make.actor` and reference-consuming `switch-actor`; choose actor handle/ownership semantics (including task↔actor lifetime) before implementing an actual scheduler. The COP [`task/step/continuation lineage`](https://github.com/JeanHuguesRobert/inseme/blob/main/packages/cop-kernel/docs/task-step-continuation-lineage.md) is the higher-level distributed continuation interface, not a replacement for the in-VM local scheduler.
   - **L9 task ownership and local scheduler FBF (2026-11-24, GPT-6 under Jean Hugues Noel Robert):** corrected the mismatched public `actor` primitive (formerly a raw integer vs the typed `make.actor` reference) to return a pinned typed reference and transfer/release the VM-owned actor pin after `switch-actor`. To avoid strong refcount cycles, a task OWNS its actor, while actor slot `+7` stores its immutable integer task id instead of a back-reference. L9 resolves that id through the **VM-local** `l9-task-registry`, which owns active task references and clears them on success/failure; child tasks have an integer `parent-id` instead of a strong back-reference to a parent that already owns its `subtasks`. The root, which is executing the CLI, now starts unpaused. The local `l9-ready-queue` is a genuine FIFO: `task.schedule` deduplicates wakes, `pause` makes a task ineligible, `resume` requeues it, `l9-next-ready` ignores stale paused/canceled/done entries, and `l9-dispatch-next` switches real actors with preserved IP/TOS/CSP and per-actor locals. `make_actor` installs an initial top-level return continuation for non-root actors; `l9-actor-finish` marks them terminal, unregisters them and resumes the next ready task (or yields back to the host when quiescent). **Verified live**, not only in mocked function tests: round-robin sequence `ABRabrQ`, task identities `A2B3R1`, suspended locals `AR41r`, and automatic two-child completion/registry cleanup `ABR11voidvoid`. A real actor scheduler **exists for cooperative workloads**; it is not preemptive, timer-based or a distributed COP scheduler.
   - **L9 fail-early exception delivery FBF (2026-11-24):** `task.raise(reason)` records an asynchronous pending error and schedules the target; at the next scheduler selection, `deliver-error` finishes it **without running its normal code**, retains the reason, unregisters it once and reports it in its parent's `failed-children` collection. `task.cancel` on a child now raises `/canceled` through that same route; repeated raise is idempotent. A failed worker does not stop a runnable sibling (live result `GOODR11`). This is a first **terminal failure-event and parent-notification** contract, not yet L8's full catch/finally/step graph, resumable exception handling or supervisor-policy escalation. The actor ownership/ABI suite is **7/7**, task structures/collections **44/44**, cooperative ready-queue **21/21** and fail-early delivery **12/12**. FBF also corrected two required collection primitives: `queue.pull` previously freed a queue reference before consuming its FIFO elements and misunderstood an extensible forwarding area; `array.put` previously wrote to the forwarding wrapper instead of the backing array. Both have real regression cases.
   - **L9 VM exception boundary and promise-to-task delivery FBF (2026-11-24, GPT-6 under Jean Hugues Noel Robert):** `run-guarded(body, on-error)` stores an actor-local recovery continuation on the **existing control stack** (saved return IP, saved data-stack top, and owned body/handler cells); on ordinary return it releases its frames, and `vm-raise(reason)` unwinds only to the nearest guard, releases nested references, restores the caller stack and runs the error handler. The bootstrap `FATAL` language hook now calls this common VM primitive. `promise-handler.schedule` guards both success and rejection callbacks: a callback error **rejects the dependent promise** with its reason, and siblings/subsequent callbacks continue. Without a local guard, a child actor enters the existing `task.raise → ready queue → deliver-error` path, reporting its failure to its parent without executing the compromised child continuation. The same raised error therefore serves guarded promises and task supervision, rather than two unrelated error engines. The root still fails explicitly when unhandled; the TS VM marks the host exit code, and the CLI no longer overrides it with `process.exit(0)`. `npm run test:inox-guarded-exceptions` passes **12/12** (nested guards, repeated calls, caller-stack depth, minimal bootstrap, real actor switch, unhandled-root failure), `npm run test:l9-promise-chain` **29/29** (including errors and recovery), and `npm run test:l9-error-delivery` **16/16** (including child isolation and deferred reporting). The lifecycle probe now passes **4/4**. This verifies the TypeScript VM and its bootstrap, **not the distinct native-JavaScript Cell representation nor all binary/native backends**. Neither per-call/defer checks nor overflow monitoring were introduced.
   - **Earlier unresolved exception surface, before the subsequent FBF:** At this checkpoint, the high-level `try:catch:` / `try:finally:` forms still depended on the unimplemented `try-run`; the reusable VM guard alone did not prove that those forms worked. Exceptions caused by fatal internal VM invariant violations are intentionally not converted into ordinary application failures. Promise-result assimilation when a callback returns another promise, task `join`, supervised catch/finally, step-level retry/recovery, and lifecycle release of parent-retained completed children remain open. The legacy `missing-method` reporter may still emit a nested-scope assertion after its diagnostic. The Principal explicitly **deferred** general control-stack overflow monitoring at actor/task boundaries (`CPKT-2026-11-22-INOX-CSP-CONTEXT-SWITCH`); the present work does not reopen that investigation.
   - **Inox try/catch/finally and scope-unwind FBF (2026-11-24, GPT-6 under Jean Hugues Noel Robert):** Reconstructed the January–April 2023 design using the existing `scope`, `on-return`, `sentinel`, `long-jump` and VM-local guarded continuation. `try-run`, `try`, `try:catch:`, `try:finally:`, `try:catch:finally:` and the ordinary `raise` surface are now defined **in `lib/bootstrap.nox`**, rather than as separate TypeScript promise exceptions. `try` alone runs its block without creating a handler; `try:catch:` installs the VM guard; `try:finally:` and the combined form create a **bounded nested `scope`** and use `on-return` for the cleanup, including when the catch handler itself raises. Use `;` to end a multi-keyword expression before a following instruction (existing Inox grammar). `vm-raise` now executes encountered `on-return` finalizers in LIFO order *while their named locals remain live*, temporarily retaining the error reason in a typed control cell, before resuming the unwind or delivering it to `task.raise`. Generic nonlocal `break` and `long-jump` also execute finalizers before their destination, and `long-jump` reads the return IP from the **located sentinel**, not the current CSP cell. This introduces no per-call/per-defer hot-path checks; explicit `break`/`long-jump` now inspect the abandoned frames, and guards have a bounded setup/teardown cost. Language lookup failures (`missing-verb`, `missing-method`, `missing-operator`) use the same error/unwind path instead of unconditionally clearing both stacks. `lib/inox.ts` also corrects the reversed data-stack depth calculation in `data-depth`, `data-dump` and `clear-data`, which otherwise made positive depths assert and prevented the cleanup function from clearing live values. A root-cause probe caught a **one-cell-per-iteration data leak** caused by confusing `with` (formal-parameter marker) with `scope` in an early version of the new implementation; replaced with the actual scope primitive and verified **1,000 successful try/finally executions with unchanged data-stack depth**. The initial test suite was red at 1/16; `npm run test:inox-try-finally` now passes **41/41** across standard/minimal, catch/finally nesting, rethrows, errors inside finalizers, local-variable access, break/long-jump, task isolation, promise callbacks, numerical reasons, repeated error handling, and data/control-stack invariants. Existing actor, promise, object, bootstrap and loop regressions remain green, including **82/82** loop tests and **4/4** integration suites. **Still separate:** true supervisor-policy catch and task `join`, promise-returned-promise assimilation, and non-TypeScript backends; do not conflate the finished language-level try/catch/finally surface with those features. The Principal's deferred CSP overflow-policy investigation remains deferred.
   - **Inox source encoding:** the current parser is not robust to non-ASCII characters even in comments. Agent attribution inside `.nox` uses ASCII `Noel`; full names and richer provenance belong in the commit, issue and Cognitive Packet. The derived `stdlib.nox` has no checked-in generator today, so these fixes are attributed in the file while a reproducible generator remains future work.
   - Goal: a **dynamic system programming language** for the cognitive substrate itself.
   - **Cannot (and should not) be "obvious"**: it manipulates the richer, less usual, traceable concepts required for rational exploration at scale:
     - Continuations as first-class input/closure delivery.
     - Cognitive packets (COP) as the currency of coordination.
     - Artifacts as projections with `stabilityLevel`, `derivesFrom`, `cacheKey`, `retentionPolicy` (until_superseded / legal_hold / right_to_forget / forever ...).
     - Capitalization (lookupReusableArtifact / stabilizeTaskArtifacts), obsolescence by judgment (human or AI marking dead-ends), fork/join of cogitors.
     - Control/data plane separation, reactive sets, pressure, tasks as sagas, JobScheduler routing/retry, partial consistency as a feature for AI agents.
     - Full dynamic objects (metaclasses, `attribute`, `it-method{}`, `extend-class`, thing dispatch), actors.
     - CXU-style runtime accounting: compute budgets, mandate-bound spending, replay-safe cost tracking, no double spend, no commit without trace, and anti-gaming rules ensuring that a large budget cannot buy cognitive legitimacy.
   - This is the "substrate for the agents". The complexity is earned; the scripting layer stays obvious precisely so agents don't have to think about all of it.

Hence the two versions, as stated.

## Current state (2026)

- The minimal/CLI/scripting path is the pleasant default and is what most `.nox` examples and tools should target first.
- `cli-stdlib.nox` is the place where we improve the "obvious" surface (update ergonomics to decent-script level, agent memory/branch/turn patterns, collections, CLI I/O, and the `js.*` host bridge).
- The `js.*` bridge (`js.eval`, `js.require`, `js.get`/`js.set`/`js.call`, `js.global`, `js.new`, ...) is an explicit, first-class feature of the scripting layer. Being based on a real JS VM is considered an *advantage* for easy per-project extension (see `research/js-interop-api-for-scripting-layer.md` and `examples/js-bridge-demo.nox`).
- L9 remains opt-in. On 2026-11-26 the TypeScript reference has tested cooperative actors, task lifecycle/join, local promises, Signal/Semaphore/Mutex/Lock, Outcome/Boxon/Moxon, one-shot Parole/Whisper and dynamic actor stacks. See [dated evidence](histoire-du-developpement-inox-l9.md) and [#42](https://github.com/JeanHuguesRobert/Inox/issues/42). Full L8 parity, host-event reentry, native backends and distributed COP deployment remain separate. The reusable `parole-template` records `will` and `may` steps, then `instantiate`, `submit` or `invoke` create independent one-shot execution handles. It does not serialize submissions as the historical L8 pipe does. Its 9-case regression suite includes concurrent pending invocations, typed outcomes and repeated execution. As of 2026-11-27, `fork-join` appends a group of branch templates as a step; each receives the incoming Outcome and join delivers an ordered array of typed Outcomes after every branch settles. It does not spawn actors, and captures a shallow branch-list snapshot (branch templates themselves remain shared descriptions). The 8-case suite includes asynchronous reverse completion, nested forks and another actor settling a branch. The template method `pipe` creates a serial FIFO of independent invocations: `submit` or `invoke` returns one Boxon per input, with the next input starting after the active result is delivered. Pending entries capture their execution at submission. The 9-case suite covers typed outcomes, reentrant submission, observer failure, cross-actor completion and an iterative drain of 100 queued inputs. This is a local queue, not durable COP delivery, bounded backpressure or full historical callable pipe interoperability.
- See also:
  - `Inox#17` (the GitHub issue recording the destiny of l8 / side / hybrid / move-out-of-JS-to-Inox, with the user's "Actually, I know what I want..." statement).
  - `research/` (naming, reactive sets, rossignol criterion, task-step-continuation lineage).
  - `lib/inox.ts` (the `cli_minimal_core` guard + run_program sync entry point).
  - `bin/inox.js` (the launcher).
  - Historical banners on `l8/README.md` and `side/README.md` (local) pointing at the Inox destination.

## Migration / usage guidance

- Write agent "code" (the logic that maintains beliefs, explores paths, capitalizes, judges) in the scripting layer first. It should feel direct. When the agent/script needs "one more thing" that isn't in core + cli-stdlib yet, it reaches out explicitly via the `js.*` bridge (`js.require "foo"`, `js.eval`, property get/call on the result, etc.). This is the intended advantage of the scripting layer running on JS.
- When you need distribution, traceability, human+AI judgment in the loop, artifact retention sweeps, reactive dataflow, full actor model, or CXU-like accounting of compute under mandate — graduate the relevant pieces to the l9 + COP layer (or use the l8-face bridges from COP/inseme while Inox is stabilizing).
- Both layers are Inox (`.nox`). We avoid producing new portable JS/TS for the agent logic itself (per the overarching "move out of Javascript and move in to Inox" constraint), except for transitional COP/inseme "face" adapters and the deliberate, thin `js.*` escape hatch in the scripting layer.

## Philosophy notes

- **Occam**: two versions is the minimal cut that keeps the agent-facing surface obvious while allowing the full power of the system layer where needed. One single "obvious for everything" language would either hide the complex concepts (bad for system programming) or force agents to confront them constantly (bad for the rational exploration use case).
- **Rossignol / traceability**: all of this is recorded (this doc, the cli-stdlib banner, Inox#17, research notes, git). The dispositif must be able to produce its own attestation.
- **Carte et territoire**: the scripting layer is closer to Cogentigram (the model / the working memory the agent reasons on). The system layer deals with the full Cogentia (the territory, provenance, multiple projections, retention obligations, judgment over dead-ends).
- **Budget is not legitimacy**: CXU-style accounting should make compute scarce, attributable and traceable; it must not let the richest actor buy the result of the cognitive game. Cost creates seriousness, not authority.

See `cli-stdlib.nox` (top banner + the recall/remember/with-update/obsolete section) for the current "obvious" surface implementation.

### One-shot CLI expression versus interactive evaluation (2026-11-24)

Principal decision: compile `-e` / `--eval` expressions into a temporary verb and invoke it, since the process terminates immediately. Explicit source programs containing definitions retain their existing path. The two JS CLI entry points share this policy; the REPL and file execution are unchanged.

Separate open parser/REPL problem ([#34](https://github.com/JeanHuguesRobert/Inox/issues/34)): direct top-level `1 2 + out` and `1 + 2 out` can leave a pending infix context at EOF and assert `proxy/reference` during parser cleanup. Reproduced on Linux/Node 26 and Windows/Node 24 at `7cf6071`. Compiled `to p 1 2 + out. p` works. Do not treat per-input permanent verb creation as the interactive solution; investigate operator disambiguation and parser-state recovery independently.


### One language, several materializations — Principal decision, 2026-11-26

The scripting/system distinction is a distinction of audience and library
profile, not a fork of the language. AbstractInox source and observable
semantics are shared; the historic TypeScript packed Cells, native
JavascriptInox Cells and future C++ layouts need not share a binary ABI.
The historical implementation remains the differential reference. Preserve
working historical code; introduce primitives as actual workloads need them,
choosing Inox definitions when their measured cost is reasonable and native
host primitives where justified. Do not systematically replace working TS
primitives, or require a new allocator for short-lived scripts.

The Multitasking Kernel is strictly cooperative and non-preemptive at the
interpreter level. Explicit suspension/resumption uses VM-owned contexts,
not host green threads, native stack switching or setjmp/longjmp. The host
event loop (Node.js, browser, Deno or a future native libuv/libev/libevent
adapter) supplies events/completions and makes tasks eligible; the kernel
chooses the next runnable task at cooperative boundaries. Housekeeping and
instruction accounting are not implicit preemption. This is a direction
for the native adapter, not evidence of implemented C++ event support.

The experimental JavascriptInox milestone at [ea1da5f](https://github.com/JeanHuguesRobert/Inox/commit/ea1da5f6a0e739e332a982babc4a81f59fab066c)
supports bounded source control, blocks, dynamic locals, it binding,
named parameters, dynamic/bound verb invocation and historical definition
termination in its tested subset. See [experiment status and measurements](../experiments/javascript-inox/README.md)
and [Cogentia #291](https://github.com/JeanHuguesRobert/cogentia/issues/291).
The existing browser selector is an opt-in Reality Test, not a production
migration or proof of full L9 compatibility. Method/class dispatch is next.


### Aggregation and selection (2026-11-27, Inox #42)

The corrected L8 Aggregator/Selector contract is tracked in [virteal/l8@5e68096](https://github.com/virteal/l8/commit/5e68096aad580ab3a0bc7d0600248ae15622333e). L9 `aggregator` collects ordered typed Outcomes; `aggregator-and` waits for every result, returning false on any failure, otherwise the first false-like value in declaration order or the last declared success. `selector` wraps the first delivered Outcome (including failure) as a successful outer Boxon; `selector-or` settles on the first truthy success or rejection, otherwise the last delivered false-like value. Historical empty inputs remain empty arrays for all/and and void for selection/or. Explicit `combinator-thunk` wrappers distinguish deferred computation from raw code Cells, with cycle detection. All four accept local promises, Boxons, direct Outcomes, Parole executions and values. Nested foreign thenable assimilation and host-event reentry are separate. Truth reduction uses a local predicate, not a new language-wide boolean rule.

Porting exposed leaked receivers in existing Boxon/Whisper adapters (use `class-of`, not `.class`) and incorrect float payload addressing.
